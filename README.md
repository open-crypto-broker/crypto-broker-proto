# Crypto Broker Protobuf

This repository contains the definitions for the protobuf messages that will be shared across the Crypto Broker clients and the server. This repository is imported as a Git submodule on each client and server in order to use the exact same version on all apps.

## Message structure

The definitions are split into an application-facing crypto service (`CryptoGrpc`), intended for client applications, and an internal development service (`CryptoGrpcDev`), used for benchmarking and testing.

### Shared messages

- **Metadata**:
  Contains basic information about a request, such as a unique ID.
  This helps track and identify requests.
  It optionally carries a `DeprecationWarning` (attached to every response produced with a deprecated profile) and a `TraceContext`.

- **CryptoDescriptor**:
  Self-describing record of how a stored artifact was produced (see ADR 0013).
  It holds the `profile`, the `operation` that produced the artifact (e.g. `HashData`, `SignCertificate`, `EncryptData`) and the concrete `algorithm` actually used (e.g. `sha3-512`, `aes-gcm`).
  It should be persisted by the caller alongside the value so the artifact stays verifiable and migratable without access to `Profiles.yaml`.

- **DeprecationWarning**:
  Deprecation signal for a profile scheduled for a rolling migration (see ADR 0013). It carries the deprecated `profile`, an optional `replacedBy` pointing to an equal-or-stronger profile, and optional `deprecatedSince`, `removeAfter` and `reason` fields.

- **TraceContext**:
  Holds trace context for manual propagation across services, including the trace ID, span ID, trace flags, trace state and a correlation ID.

### Key material and crypto parameters

- **KeySource**:
  Key material source for symmetric encryption/decryption. Exactly one variant is set, governed by the profile: `rawKey` for caller-managed profiles (no KMS) or `keyId` for KMS profiles, where the broker resolves the identifier and retrieves the externally provisioned key. The broker never creates, imports or deletes keys; key lifecycle is owned by the KMS/operator.

- **SignKeySource**:
  Signing key material for `SignData`/`VerifyData`. Legacy and post-quantum modes use a single `KeySource`; hybrid (composite) mode uses two component keys via `ComponentKeys`. For `VerifyData` the key sources carry the corresponding public keys.

- **ComponentKeys**:
  Ordered list of component key sources for hybrid (composite) signing: the traditional key followed by the ML-DSA key.

- **EncryptMetadata**:
  Caller-supplied encryption parameters. The `nonce` is always provided by the caller (neither the broker nor the KMS generates it, so the caller owns nonce-uniqueness) and the `aad` is optional.

- **CipherMetadata**:
  Metadata returned alongside the ciphertext by `EncryptData`. It echoes the `keyId` (for KMS profiles), the `nonce` and optional `aad`, and the authentication `tag` that the caller must retain to decrypt later. Key material is never returned.

- **DecryptMetadata**:
  Caller-supplied parameters for `DecryptData`, symmetric to `EncryptMetadata`. The caller provides the `nonce`, optional `aad` and `tag`, typically by echoing back the values from the `CipherMetadata` receipt returned by `EncryptData`.

### Output formats

- **HashOutputFormat**:
  Selects the encoding of the returned hash value: `HEX` (default) or `RAW`.

- **SignOutputFormat**:
  Selects the encoding of the returned signed certificate: `DER` (default) or `PEM`.

- **SignatureFormat**:
  Output format for signatures produced by `SignData` and accepted by `VerifyData`: `SIGNATURE_RAW`, `SIGNATURE_DER`, `SIGNATURE_PEM` or `SIGNATURE_CMS`. `SIGNATURE_CMS` wraps the signature in an RFC 5652 CMS `SignedData` structure; the other formats carry the bare signature value in the requested encoding.

- **MessageSizeLimit**:
  Single source of truth for gRPC message size limits, applied as transport options in the server and clients. It defines the maximum request accepted from client to server (2 MiB) and the maximum response returned from server to client (1 MiB).

### Application-facing service: `CryptoGrpc`

#### `CryptoGrpc` messages

- **HashDataRequest**:
  Used to ask the server to hash some input. It includes the Crypto Profile to use, the input to be hashed, the desired output format and a Metadata.

- **HashDataResponse**:
  Contains the resulting hash value (as hex or raw bytes), the used hash algorithm, a `CryptoDescriptor` and Metadata about the hashing process.

- **SignCertificateRequest**:
  Used to request a digital signature for a certificate signing request (CSR). It includes the Crypto Profile, CSR data, signing key, validity period, CA certificate, the desired output format and Metadata. Optionally, a subject and CRL distribution point URLs can be added.

- **SignCertificateResponse**:
  Contains the signed certificate generated by the server (as PEM or DER), a `CryptoDescriptor` and the metadata.

- **SignDataRequest**:
  Used to request a digital signature over arbitrary input. It includes the Crypto Profile, the `SignKeySource`, the input to sign, an optional `SignatureFormat` and Metadata.

- **SignDataResponse**:
  Contains the resulting signature, a `CryptoDescriptor` and Metadata.

- **VerifyDataRequest**:
  Used to verify a signature over some input. It includes the Crypto Profile, the `SignKeySource` (carrying the public key(s)), the input, the signature to check, an optional `SignatureFormat` and Metadata.

- **VerifyDataResponse**:
  Contains a boolean `valid` indicating whether the signature is valid, along with the Metadata.

- **EncryptDataRequest**:
  Used to encrypt some plaintext. It includes the Crypto Profile, the `KeySource`, the plaintext, the caller-supplied `EncryptMetadata` and Metadata.

- **EncryptDataResponse**:
  Contains the resulting ciphertext, the `CipherMetadata` receipt, a `CryptoDescriptor` and Metadata.

- **DecryptDataRequest**:
  Used to decrypt some ciphertext. It includes the Crypto Profile, the `KeySource`, the ciphertext, the caller-supplied `DecryptMetadata` and Metadata.

- **DecryptDataResponse**:
  Contains the recovered plaintext and the Metadata.

#### `CryptoGrpc` functions

- **HashData**:
  Takes a `HashDataRequest` and returns a `HashDataResponse`. This is used to generate a hash of the provided input using the hashing algorithm specified by the profile.

- **SignCertificate**:
  Takes a `SignCertificateRequest` and returns a `SignCertificateResponse`. This is used to sign a CSR based on the profile's settings and return the signed certificate.

- **SignData**:
  Takes a `SignDataRequest` and returns a `SignDataResponse`. This is used to produce a digital signature over the provided input using the key material and algorithm specified by the profile.

- **VerifyData**:
  Takes a `VerifyDataRequest` and returns a `VerifyDataResponse`. This is used to verify a signature over the provided input against the supplied public key(s).

- **EncryptData**:
  Takes an `EncryptDataRequest` and returns an `EncryptDataResponse`. This is used to encrypt the provided plaintext using the key material and algorithm specified by the profile.

- **DecryptData**:
  Takes a `DecryptDataRequest` and returns a `DecryptDataResponse`. This is used to decrypt the provided ciphertext using the key material and algorithm specified by the profile.

### Internal development service: `CryptoGrpcDev`

#### `CryptoGrpcDev` messages

- **BenchmarkRequest**:
  Request a performance benchmark from the server.

- **BenchmarkResponse**:
  The result of the Crypto Broker server performance benchmark.

- **FakeEndpointRequest**:
  Used to invoke a fake endpoint for testing and connectivity checks.

- **FakeEndpointResponse**:
  Contains a message returned by the fake endpoint along with the metadata.

#### `CryptoGrpcDev` functions

- **Benchmark**:
  Takes a `BenchmarkRequest` and return a `BenchmarkResponse`. This is used to get performance overview of the different cryptographic algorithms and functions.

- **FakeEndpoint**:
  Takes a `FakeEndpointRequest` and returns a `FakeEndpointResponse`. This is used for testing and connectivity checks.

## Protobuf as a submodule

To add this to your project as a submodule you can run this command from the repository where you want to add it. Please change the URL for this repository's URL and establish the subfolder where you want to save this inside your project.

```shell
git submodule add https://github.com/open-crypto-broker/crypto-broker-proto <sub/folder/protobuf>
```

To fetch the latest commit from this repository, you can just run:

```shell
git submodule update --init
```

This will fetch the latest changes. Moreover, VS Code provides already functionality to fetch the code if you go to the `Source Control` section of VS Code.
